Morpheus 性能优化研究实践 Road Map

目标是在周一至周五、每天 10:00–19:00 的约束下，尽快完成 100 位员工、13 周的正常行为轨迹模拟。本文只记录性能优化路线，回答四个问题。原始路径慢在哪里，调研到了什么方法，实际采用了哪些部分，最终测到了什么效果。

版本 v3 · 2026-11-20 · 真实模型端到端结果与 stub 结果分开记录

最终结论先行

结论边界 当前已经完成的是规模化工程路径和 stub 回归。真实模型下的 100 人端到端运行尚未完成，因此真实模型耗时仍是估算，不能把 stub 的速度当作模型加速比。

当前可复现结果

100 人 × 13 周 × 5 个工作日 × 4 个事件，共 26,000 个事件。8 个 worker 下 100 个员工 batch 全部完成，manifest 报告 0 失败，stub 端到端约 1.1 秒。

调用粒度变化

在同一测试夹具中，原始逐复杂事件路径最多需要 13,000 个复杂事件入口。新路径把模型 handoff 压缩为 100 个员工级 batch，减少的是调用粒度，不是已经测得的真实模型时间。

真实时间估算

已有完整日程时，行为执行阶段预计约 40–60 分钟。从画像、计划、日程到行为执行的完整流程预计约 2–5 小时，需用真实网关小样本校准。

路线总览

0测量基线时间、调用、失败
1事件驱动移除空转等待
2长周期批处理减少模型入口
3有界并发提高吞吐
4阶段并行缩短关键路径
5隔离与汇总控制尾延迟
6真实基准确认最终收益

每一步都按“瓶颈 → 调研方法 → 采用部分 → 代码修改 → 测量结果 → 下一步”推进。阶段 1 至阶段 5 已有工程实现，阶段 6 是真实网关下的性能验收。

阶段 1 · 事件驱动仿真替代时间驱动循环

调研采用的思想实际修改最终效果尚未完成
SimPy 的 event scheduling 和离散事件仿真仿真时钟直接跳到下一个事件，不为没有事件的时间片执行真实等待。scale_simulation.py 通过 _load_horizon 读取、夹紧并排序日程事件，直接回放事件时间。规模入口不再执行 13 周的 sleep(1) 空转，也不再逐秒推进逻辑时钟。尚未在同一真实模型夹具上测原始 daily runner 与新入口的 wall time 差值。

采用的是事件调度思想，使用的是现有 JSON 日程和轻量排序，没有引入 SimPy runtime。这样保留了最小改动，也避免把模型调用塞进另一个仿真框架。

阶段 2 · 员工级长周期批处理替代逐事件模型调用

调研采用的思想实际修改最终效果尚未完成
MapReduce 的 map / reduce 任务组织把彼此独立的员工 horizon 作为 map 任务并发处理，再由 manifest 聚合结果。批次边界应对应可恢复、可审计的工作单元。_run_member 为一名员工加载完整 13 周并完成一次 human-planner → tool-agent handoff。主函数聚合每位员工结果生成 manifest.json。测试夹具中 13,000 个潜在复杂事件入口变为 100 个员工 batch，调用粒度降低 130 倍。每个员工仍保留逐事件 trajectory。还没有真实模型下的 token、网络时间和成本对照，不能把 130 倍写成 130 倍加速。
N_events = 100 × 13 × 5 × 4 = 26,000
N_complex_fixture = 100 × 13 × 5 × 2 = 13,000
N_horizon_batches = 100
granularity_reduction = 13,000 / 100 = 130

阶段 3 · 有界并发替代无限制 fan-out

调研采用的思想实际修改最终效果尚未完成
Python ThreadPoolExecutor、Little 定律和 Amdahl 定律网络等待型任务适合线程并发，但 worker 数应由吞吐、队列和共享资源约束。并行只能加速可并行部分，不能消除串行关键路径。画像、周汇总、部门会议和 horizon batch 使用有界线程池。默认 MORPHEUS_SCALE_WORKERS=8，用 as_completed 回收结果。避免一次性创建无界任务。stub 规模回归中 8 worker 完成 100 个员工 batch，0 失败。尚未用真实网关比较 8、12、16 worker 的吞吐曲线、限流和 p95。

这里采用的是有界 fan-out/fan-in，不是简单地把 worker 数调到最大。最终 worker 数必须由真实网关的吞吐和尾延迟实验确定。

阶段 4 · 启动阶段按依赖图并行

调研采用的思想实际修改最终效果尚未完成
Map-style fan-out、fork–join 和关键路径分析只有相互独立的任务并行，依赖阶段保持顺序。并行目标是缩短关键路径，不是让所有请求同时发送。profile_generation.py 画像分批并行。post_meeting_summary_auto.py 按周并行。hierarchical_meeting.py 在 head council 完成后并行部门会议。daily_plan_generation_auto.py 按员工–周并行。启动阶段从串行循环改为多个有界 fan-out 阶段。画像生成还按批刷新上下文，避免所有线程共享同一个空快照。阶段级真实 wall time 尚未记录，完整流程仍受约 1,300 个员工周日程请求限制。
T_total ≈ T_company + T_profiles/8 + T_meetings + T_weekly_summaries/8 + T_daily_plans/8 + T_horizon/8
优化重点是缩短可并行项，不能把所有阶段相加后再宣称并行收益。

阶段 5 · 以尾延迟控制和任务隔离保证规模运行不被单个员工拖住

调研采用的思想实际修改最终效果尚未完成
Google Tail at Scale 与 MapReduce 的任务隔离思想批次应该独立失败和独立记录，单个慢任务不能覆盖其他结果。共享状态要隔离，结果要可聚合。每位员工写独立目录、horizon_result.json、trajectory 和审计 CSV。Harness home 按进程和线程隔离。manifest 汇总完成数、失败数和耗时。单个员工的结果具备独立审计边界。测试中 100 个 batch 均完成，manifest 能记录每个成员状态。当前没有 hedged request、自动重试和真正的 checkpoint resume。失败后的重试策略仍需补充。

阶段 6 · 输入预检和性能证据闭环

调研采用的思想实际修改最终效果尚未完成
性能实验中的 workload 固定、Amdahl 分解和可复现 manifest在昂贵运行前固定人数、周数、工作日和时间边界，记录输入规模、并发度、完成数和耗时。scale_simulation.py 启动前检查员工数和日程文件树。manifest.json 记录 workload、workers、events、batches、完成数、失败数和 elapsed time。当前 5 人旧样例会在模型调用前被拒绝，不会静默生成“100 人完成”。stub 回归有完整规模证据。真实模型基准还需加入 token、重试次数、网关状态码、p50/p95 和成本。

调研过但本轮没有采用的方法

方法为什么调研为什么没有采用后续触发条件
SimPy 或完整 DES runtime可以提供成熟的事件队列和仿真时钟。当前规模入口只需要读取已有日程并回放，新增 runtime 会扩大改动面，不能直接减少模型网络时间。需要资源竞争、插队、延迟和实时交互仿真时再引入。
asyncio 全异步调度可能降低等待期间的线程开销。现有 Harness SDK 调用是同步上下文，先使用有界线程池能保持改动最小。真实基准显示线程调度成为瓶颈时再评估。
vLLM / Orca continuous batching服务端连续批处理能提升 Transformer 推理吞吐。当前模型网关和 Harness runtime 的服务端调度不可由仓库控制，客户端伪造 batching 不能保证语义等价。能够控制模型服务部署并且有批量 API 时再做服务端实验。
Celery、Ray 或多机调度可以扩展到多主机和大规模队列。当前目标是单机 100 人，增加分布式系统会引入部署、重试和一致性成本。单机 16 worker 仍无法满足真实 SLA 时再引入。
模型结果缓存重复 prompt 可以减少模型调用。员工画像、权限、日程和历史状态具有上下文依赖，盲目缓存会破坏轨迹差异和审计真实性。只对完全相同的结构化输入做显式 cache，并记录 cache provenance。

性能调研来源

来源本项目采用的认识代码中的对应部分
SimPy time and scheduling事件调度器应推进到下一个事件，避免无事件时间片空转。_load_horizon 直接读取、夹紧和排序日程。
MapReduce独立任务可以 map 式 fan-out，结果可以 reduce 式聚合，任务边界适合故障隔离。员工级 horizon batch、ThreadPoolExecutor、manifest.json。
Python concurrent.futures使用有界线程池管理 I/O 等待和结果回收。画像、计划、会议和规模入口的线程池与 as_completed。
Amdahl's law 与 Little's law并发只能优化可并行部分，worker 数必须结合吞吐、队列和等待时间分析。阶段依赖拆分、8 worker 默认值和下一轮 1/2/4/8/12/16 实验。
The Tail at Scale大规模 fan-out 的总延迟受慢请求支配，必须记录尾延迟并隔离慢任务。每员工独立结果、Harness home 隔离、manifest 记录成员耗时。
MapReduce fault tolerance失败任务应有独立边界，后续可按任务重试，不必重做整个作业。当前已实现 per-member error 和 manifest，自动 checkpoint/retry 仍是下一步。
最终边界 当前可以确认的是性能工程路径和 stub 规模结果。真实模型的最终性能必须由 P1 至 P4 测量，特别是网关限流、p95、token、失败重试和完整启动阶段耗时。当前页面没有把任何未运行的性能方法写成已完成结果。
