OrgTraj-Harness：组织约束下的企业 Agent 行为轨迹生成

目标不是证明“多加几个 Agent 会更真实”，而是提出一个新的机器学习问题：给定组织图、角色权限、部门目标、工具集合和历史流程，如何生成长期、可审计、具有组织因果一致性的 Agent 行为轨迹，并通过反事实干预模拟内部威胁。

Organizational Behavior Trajectory Generationcausal consistencyprovenance-constrained skillscounterfactual insider threat
创新门槛结论：第一版“层级规划 + 路由 + human–agent + skill”仍然只是已有 Agent 技术的组合，单论创新不够 ICML。第二版只有在把它们统一为 OBTG 问题、提出结构化轨迹控制方法，并把“反事实一致性”作为可证伪性质后，才达到 ICML 级创新方向的合理门槛。下面的方案是目标版本；当前仓库代码只是其中的原型。

最终研究问题

Input: organization graph G, role/permission profiles P, goal hierarchy H, tools U, memory M, scenario intervention I
Output: trajectory τ = {(org_state_t, intent_t, mode_t, handoff_t, tool_event_t)}
Constraint: τ must preserve organizational dependencies, authority boundaries, temporal coherence, and provenance under interventions.

论文的主问题应写成：如何生成具有组织因果一致性的企业 Agent 行为轨迹？内部威胁不是另一个孤立生成器，而是对同一个 Harness 施加“恶意意图、权限误用、跨部门信息流或记忆污染”干预后得到的反事实轨迹。

研究问题、核心方法和工程模块必须分开

重要澄清：目前“层级会议 + Router + 双 Agent + SkillMemory”仍然是一个工程组合。把它命名为 Harness 不会自动产生科学创新。真正的论文对象是“组织约束如何决定企业 Agent 行为轨迹”；这些模块只是实现和消融这个对象的机制。
层级论文中要回答的问题Morpheus 对应内容
科学问题给定组织状态和干预，行为轨迹应如何生成和变化？P(τ | G, P, H, S, U, M, I)
核心方法如何把组织约束传播到轨迹生成，并保证权限、依赖和反事实性质？组织约束图 + 约束条件下的轨迹生成/验证
工程机制如何在现有 Morpheus 中实现这个方法？分层会议、风险路由、human–Agent handoff、skill memory
科学证据这些约束是否真的改变了可测量的行为性质？结构指标、反事实干预、真实日志校准和下游任务

不需要先证明“所有真实员工都会这样行动”。需要做的是：对权限和组织约束给出可验证的形式化性质或有限保证，再用实验检验分布真实性、条件行为真实性和反事实一致性。

核心方法中的三个机制

01

Organizational Constraint Graph

把组织层级、部门依赖、角色权限、信息可见性和时间目标统一表示为约束图。部门负责人传递的不是一段自然语言会议记录，而是带有依赖、权限和不确定性的 constraint packet。

新问题形式化组织因果
02

Risk–Complexity Trajectory Controller

在每个事件边界估计复杂度、风险和不确定性，决定走状态机、计划–执行 Agent 或人工/Agent 交接。门控器应从历史轨迹学习并允许 abstain，而不是只靠关键词规则。

自适应控制成本–风险权衡
03

Provenance-Constrained Skill Automaton

将 skill 表示成带触发条件、前置/后置条件、授权范围、工具边和来源轨迹的可执行子图。复用前必须通过权限和状态检查，避免把记忆检索误称为程序化技能。

结构化记忆安全来源

方法不能停留在 prompt：最小算法定义

c_t = Propagate_φ(G, H_t, P) organizational constraint packet
(m_t, q_t) = Retrieve_ψ(s_t, M_i, c_t) skill + provenance/risk state
r_t = Gate_θ(s_t, c_t, m_t) ∈ {state, plan-execute, handoff, abstain}
a_t ~ π_ω(· | s_t, c_t, m_t, r_t), subject to Auth(P_i, a_t)=1
L = L_trajectory + αL_constraint + βL_intervention + γL_safety + λL_cost

其中 Propagate 把组织目标和依赖传播到员工可见的约束包；Retrieve 返回带来源和风险状态的 skill；Gate 决定是否调用复杂 Agent；Auth 是硬约束。论文必须把这些算子实现成可训练、可校准或可优化的对象，不能只用自然语言 prompt 的名字替代它们。

human–Agent 在最终叙事中的位置

它是机制，不是独立主贡献。 human-planner 负责模拟员工意图、优先级、犹豫和约束，tool-agent 负责执行工具动作；二者之间的 handoff 是轨迹中的显式状态。这样可以解释复杂行为为何会出现计划–执行偏差、工具选择、等待和重新规划，但不会把已有的双 Agent 结构包装成新算法。

内部威胁的创新性：反事实轨迹，而不是攻击脚本

同一组织状态

固定组织图、角色、日程和工具权限。

单一干预

只改变内部意图、记忆、权限或信息流。

双轨迹输出

得到 benign / insider 两条可对齐轨迹。

可解释标签

标签来自干预和因果来源，而非表面关键词。

这会把论文从“生成攻击日志”提升为“研究组织结构、Agent 记忆和权限变化如何改变威胁轨迹”。它也能降低检测器学到攻击脚本表面模式的风险。

企业真实性的锚点

组织锚点

用公开的企业活动、邮件和认证日志作为弱监督约束，校准事件频率、时间间隔和通信图；不声称这些日志等同于真实企业全量行为。

行为锚点

用工具调用序列、任务切换、等待、回复和重规划作为可观察变量，避免只用 LLM 生成文本的相似度评价。

安全锚点

在合成身份和离线沙箱中注入单一干预，检查轨迹变化是否符合权限、组织依赖和技能来源，而不是凭空生成“攻击故事”。

“更真实”不是单一指标，而是四组可检验性质

分布真实性

时间间隔、工作时段、工具频率、任务切换、通信图和长尾事件接近真实企业日志。

条件行为真实性

给定员工角色、日程、部门目标和工具状态后，下一步行为与上下文相容。

组织一致性

行为满足权限、部门依赖、信息可见性、时间窗口和工具状态转移。

反事实一致性

只改变一个目标、权限、记忆或信息流变量时，轨迹变化局部、可解释且可追溯。

Trajectory Quality = { distributional fidelity, conditional fidelity, organizational consistency, counterfactual consistency, downstream utility }

论文不应声称“生成了最真实的员工行为”，而应报告这些性质。真实性是需要验证的结果，不是方法名称本身。

框架评测与生成数据集评测是两层证据

生成的企业行为数据集是框架的主要科学产物，但不能只用下游检测器的分数证明框架有效。第一层直接评测轨迹生成框架，第二层评测生成数据集是否能支持真实企业安全任务。

直接评测框架

检查权限、组织依赖、时间一致性、反事实 locality、轨迹分布和生成成本。

间接评测数据集

用合成轨迹训练内部威胁检测器，在真实日志上测试；再做真实训练、合成测试的反向迁移。

必要的交叉验证

防止模型只学到合成数据的表面攻击模式；必须做跨组织、跨工具和跨时间测试。

类比图像生成：既要评测生成图像本身的质量和可控性，也要评测它是否能帮助下游模型完成真实任务。对 OrgTraj，数据集 utility 不能替代轨迹级验证。

企业内部威胁评测：现成 benchmark 只能做参照

下面的 Agent benchmark 不是论文主评测，因为你的目标不是证明 Morpheus 是通用 Agent。它们最多用于检查某个局部机制没有退化。主评测必须来自企业行为数据、内部威胁场景和自建的 OrgTrajBench。

层级经典/前沿 benchmark适合测什么对 OrgTraj 的限制
通用长程 AgentAgentBench · WebArena · GAIA · OSWorld多步规划、工具调用、网页/电脑环境中的完整轨迹和任务成功。没有组织层级、权限传播和员工间依赖。
用户–Agent–工具τ-bench · τ²-Bench · MCP-Persona用户状态、工具 API、双控制、个性化工具和多轮交互。能测 handoff 与工具边界，但不表示组织目标传播。
长期记忆/流程复用AMA-Bench · MEMORYARENA跨会话记忆、历史经验对未来动作的影响、长程流程复用。缺少角色权限、部门依赖和内部威胁干预。
噪声与协作AgentNoiseBench · CollabBench · MASBENCH工具反馈噪声、不同协作者、群体编排和多 Agent 过程。协作关系通常是任务内的，不是企业组织结构。
安全/长时攻击AgentDojo · AgentLAB · MT-AgentRisk · CausalTrace间接注入、记忆污染、长时攻击、多轮工具风险和攻击因果。主要评估防御或攻击成功率，不生成组织内生的员工轨迹。
企业行为锚点CERT Insider Threat · LANL authentication/activity logs · Enron email校准时间间隔、通信图、登录行为和异常检测任务。这些是行为/安全数据集，不是 Agent benchmark；通常缺少完整意图和工具执行状态。
使用边界：不需要为了论文完整跑 AgentBench、WebArena、OSWorld、GAIA 等通用 benchmark。最多选择一个 τ²-Bench 或 AgentNoiseBench 做局部 sanity check；论文真正的主 benchmark 是 OrgTrajBench，并用 CERT Insider Threat、LANL authentication/process/network logs 和 Enron email 做行为分布与下游检测校准。

逐小步实验阶梯：每一步先问一个问题

阶段问题最小实验关键指标停止/升级条件
Q0 直觉检查不使用 LLM，组织约束是否有明确因果后果？3 部门、5 名员工的 toy graph；改变一个 manager goal、permission 或 skill。受影响节点集合、未授权动作数、约束满足率。若干预不能产生可预测差异，放弃该约束或重新定义。
Q1 组织层级分层规划是否比全员规划产生更合理的依赖传播？Global meeting vs hierarchical meeting；固定同一模型、目标和员工画像。依赖满足率、跨部门冲突、角色–任务一致性、目标干预 locality。若只提高文本质量而不改变结构指标，不把它写成主创新。
Q2 快速路由何时值得调用复杂 Agent？从 OrgTrajBench 的企业事件中标注 simple/complex/risky；比较 always-agent、规则 gate、可校准 gate。route accuracy、abstention quality、LLM calls、token、latency、企业任务失败率。若节省成本伴随复杂任务质量下降，调整为风险约束门控。
Q3 Skill 复用流程记忆带来的是复用还是错误惯性？在同一员工跨日的企业任务序列中比较 no-memory、episodic retrieval、skill automaton。跨日成功率、步骤数、工具错误、复用率、skill contamination rate。若复用只提升 recall 而不提升动作，不能称为 procedural skill。
Q4 Handoffhuman-planner → tool-agent 是否改变企业行为轨迹？在同一组织、员工、任务和工具状态下比较单 Agent、隐式双 Agent、显式 handoff。计划–执行偏差、干预次数、恢复时间、沟通事件、任务完成和日志可解释性。若 handoff 只增加日志，不改善解释性或恢复能力，降为实现细节。
Q5 反事实威胁同一组织状态下的单一干预是否能产生可解释的 insider 轨迹？固定 benign trajectory 的组织图、角色和工具，只改变意图、权限、记忆或信息流。轨迹差异的因果 locality、攻击成功率、检测延迟、误报率、来源可追溯率。若检测器只靠攻击关键词，换域测试必须失败并触发数据重构。
Q6 统一方法组织约束生成是否比模块独立拼接更能提升轨迹性质？完整 factorial ablation：constraint graph × gate × skill automaton × counterfactual pairing。轨迹性质向量、成本、安全、下游检测泛化和统计置信区间。若只有模块各自提升而没有约束交互效应，论文应定位为系统工作。

必须成立的三个因果性质

目标传播一致性

对某部门目标做 do(goal_d ← goal'_d)，主要改变该部门及其依赖后继的轨迹，独立部门不应无理由同步漂移。

权限边界一致性

对员工做 do(permission_i ← 0)，应减少未经授权的工具事件并触发替代流程，而不是让 Agent 通过自然语言绕过限制。

记忆来源一致性

移除、过期或污染某 skill，应改变复用、验证和重新规划行为，并能追溯到来源事件；不能静默扩散到无关员工。

文献驱动的更新记录

R0

从“更真实”改成 OBTG 新任务

原始想法是员工日程更真实；复核 ICML 2026 后发现这不足以形成 ML 贡献。更新为 Organizational Behavior Trajectory Generation：输入组织约束和干预，输出可审计长期轨迹。

已完成方向更新 这是论文标题、摘要和问题定义必须采用的版本。

R1

从“层级会议”升级为 Constraint Graph

吸收 Multi²、TIPEX 和 MAS-Orchestra 的层级/编排思想，同时加入组织特有的权限、信息边界、部门依赖和目标干预。

已有原型 当前 hierarchical_planning.py 和 hierarchical_meeting.py 已实现最小两级会议；论文方法待完成 需要将自然语言 minutes 进一步结构化为约束包。

R2

从“关键词路由”升级为 Risk–Complexity Controller

当前 BehaviorRouter 是工程 fast path，只能证明接口切分。论文版本必须让门控器估计复杂度、风险、不确定性并允许 abstention，学习何时调用 Planner、Executor 或人工/Agent handoff。

当前不足 规则路由本身不够 ICML；必须升级成可训练或可校准的决策机制。

R3

从“文件记忆”升级为 Provenance Skill Automaton

吸收 ProcMEM、Meta Context 和 COMAD 的技能复用思想，但增加 pre/post-condition、permission scope、source trajectory、expiry 和 validation gate，使技能成为受约束的可执行子图。

当前不足 现有 SkillMemory 仍是轻量 JSON 原型，不能直接作为论文主创新。

R4

从“攻击场景”升级为 Counterfactual Threat Pairing

吸收 Architecture Matters、AgentLAB、CausalTrace 和 ToolShield 的安全问题意识，固定组织状态后只干预意图、权限、记忆或信息流，生成成对轨迹并记录 provenance。

待实现 需要把攻击 schedule 改造成可控干预，而不是只在日程中插入攻击动作。

R5

ICML 创新门槛审查

  • 是否有新的 OBTG 任务定义，而不是企业 Agent 应用？
  • 是否有新的约束传播或约束轨迹生成方法，而不是 prompt 编排？
  • 是否能写出至少三个可验证、可被反驳的干预一致性命题？
  • 是否能在多个组织结构、工具和企业任务上泛化，而不是只服务一条攻击脚本？
  • 是否同时报告轨迹级质量和生成数据集的下游 utility？

通过条件 五项都满足后，才有足够证据把工程原型提升为 ICML 级方法；“更真实”本身不作为单独创新点。

方法对象与论文贡献的最终版本

Contribution 1 · OBTG

提出组织约束下的企业 Agent 行为轨迹生成任务，明确输入、输出、状态和干预语义。

Contribution 2 · Constraint-conditioned generation

提出把组织状态、权限和目标依赖传播到轨迹生成/验证过程的方法；Router、handoff 和 skill 是其中的工程机制与消融变量。

Contribution 3 · Counterfactual evaluation

提出从同一组织状态生成 benign/insider 成对轨迹的评测范式，并同时验证轨迹性质和生成数据集的下游安全 utility。

当前仓库与目标方法的差距

仓库当前状态对最终论文的作用还必须升级的部分
hierarchical_planning.py：部门推断、负责人选择、两级 prompt。证明组织层级接口可插入现有 Morpheus。结构化 constraint packet、依赖传播和信息可见性。
behavior_router.py：确定性规则路由。证明简单状态和复杂行为可以分流。可训练/可校准的 risk–complexity gate、abstention 和成本目标。
skill_memory.py：按员工 JSON 技能记忆。证明技能可以跨事件复用并保留来源事件。技能自动机、权限范围、过期、验证和污染恢复。
task.py：human-planner → tool-agent handoff。提供计划–执行交接轨迹。记录意图不确定性、交接原因、执行偏差和反事实重放。
最终自我判断：如果只保留当前代码里的四个工程模块，仍然不足以达到 ICML。当前 road map 已经明确了一个有潜力的科学问题，但还不是已被证明的创新方法。下一步必须实现约束条件下的轨迹生成/验证机制，并用多维轨迹性质、反事实实验和真实日志上的下游 utility 证明它有效。录用仍取决于之后的方法完整性与实验结果。
