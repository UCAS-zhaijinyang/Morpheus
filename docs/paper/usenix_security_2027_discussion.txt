6 DISCUSSION

6.1 Research significance

Morpheus-Harness extends enterprise insider-threat simulation from account-level events to an auditable execution chain. The relevant chain is `source → human principal → delegated agent/runtime → tool/API → resource or recipient → persistent memory`. A single operation can therefore involve an external document or message, an employee, a planner, a tool agent, a delegated token, and a state-changing service. OAuth token exchange and attribute-based access control provide established ways to distinguish the subject from the acting party and to evaluate authorization using subject, object, operation, environment, and policy [4,7]. Morpheus-Harness brings these distinctions into generated enterprise trajectories and adds organizational purpose and dependency to the audit unit [6].

The current implementation makes this chain observable through hierarchical planning, the human-planner to tool-agent handoff, agent registry fields, `harness_events.jsonl`, `agent_audit.jsonl`, `behavior_policy.csv`, per-member skills, and event-level trajectory records. The scale runner also demonstrates a bounded execution path for 100 employees over 13 weeks, producing 26,000 scheduled events and 100 employee batches with zero failed batches in the stub regression. This is evidence of a reproducible engineering path and artifact boundary. The reduction from 13,000 potential complex-event entries to 100 employee batches is a reduction in model-entry granularity. It is not a measured 130-fold reduction in live-model time, token use, or monetary cost.

The main methodological significance is the separation between trajectory validity and detector utility. A detector that performs well on generated data demonstrates that the data supports that detector and task. It does not establish that the generated behavior reproduces real employees. Direct evaluation must separately measure distributional and conditional behavior, organizational and temporal consistency, provenance completeness, intervention locality, executable state changes, and downstream detection utility [17,20]. The current system remains a controlled simulator. Its scenarios are selected by `src/harness_runner.py` from `threat_scenarios/`, some traces retain `Attack`, `attack_marked`, or `(Attack)` indicators, the router is keyword-based, and horizon batching does not reproduce every live cross-employee interaction. These boundaries prevent claims about real-world attack frequency or the proposition that enterprise Agents necessarily increase risk.

6.2 Future work

The first priority is to move from schedule-level attack injection to interaction-level endogenous threats. The benchmark should generate four matched conditions from the same organization state: ordinary employee behavior, benign human-agent work, an agent-mediated threat, and a traditional account-level threat. A single `do()` intervention should change only one source, delegation scope, memory item, inter-agent message, or intent. The employee and Agent should decide whether to ask, wait, delegate, retry, or proceed, and the threat should be allowed to fail. Evaluation should distinguish preconfigured activity, refused request, blocked attempt, partial disclosure, and verified state change. Metrics should include attack success, affected-resource state, detection delay, false refusal, provenance completeness, attribution ambiguity, persistence, and causal locality. This design follows dynamic tool-use evaluation and indirect prompt-injection research [10,11,23,24,28].

The second priority is to unify the Harness. An append-only event bus and shared state store should carry organization-state versions, parent events, principal and runtime identities, delegation chains, source objects, plan steps, policy decisions, tool results, memory writes, and recipients. A constraint and provenance verifier should check authorization before each tool call, validate postconditions after execution, and support checkpointing, branching, deterministic replay, rollback, and state diffs [27]. This is needed because the current outputs can disagree. In one run, a tool log reported that evidence was unavailable while a daily summary said that the evidence had been reviewed and archived. The implementation can also append `task_completed` after a failed Harness answer. A lifecycle event or natural-language summary should not be treated as proof of a business outcome.

The third priority is to replace the keyword router and lightweight skill store with security-aware control. A calibrated risk-complexity gate should estimate complexity, risk, uncertainty, expected cost, and false-refusal cost, then choose deterministic execution, plan-execute, human review, or abstention. `legacy workflow memory` should become a provenance-constrained skill automaton with activation and preconditions, typed tool edges, postconditions, permission and recipient scope, source trajectory, version, expiry, validation, revocation, and contamination state. Experiments should vary isolated, department-shared, organization-shared, and contaminated memory while holding tasks and tool permissions fixed. The resulting measures should include contamination rate, propagation depth, recovery time, unauthorized calls, and post-revocation utility [21,25,26].

The final priority is external validity. Future experiments should compare event-level and horizon-batch execution on the same world state, transfer across organizations, models, tools, and held-out time periods, and calibrate timing and communication graphs against CERT, LANL, and Enron records [2,29,30]. They should also measure membership inference, reconstruction, identity leakage, model drift, provider failure, p50 and p95 latency, token cost, and retry recovery. Synthetic identities, offline tools, and explicit threat budgets should remain the default for released artifacts.

6.3 Implications for current enterprise development

For IAM, enterprise Agents should be governed as identifiable and delegated principals. A production record should include Agent identity, owner or sponsor, lifecycle state, runtime identity, token scope, resource scope, human principal, delegation chain, purpose, and expiry. The practical control is purpose-bound least privilege with short-lived delegation and explicit recipient restrictions. Microsoft Entra Agent ID and OAuth token exchange show how the subject and acting Agent can be represented separately [7,13]. Zero Trust and ABAC provide the policy basis for checking the current user, Agent, asset, resource, operation, and workflow context [4,5].

For SOC and UEBA, the unit of analysis should become a source-to-state chain rather than a user-account pair. Investigators need source, retrieval object, prompt or message, human principal, Agent and runtime, skill version, tool call, recipient, policy decision, and resulting state. User-resource context already improves insider-threat detection [15], while monitoring AI-operated accounts shows that stateful effects and limited daily review budgets change operational recall [18]. Alert ranking should therefore combine impact, uncertainty, provenance completeness, attribution ambiguity, and review cost. A model explanation can support triage, but service state and policy evidence should confirm impact.

For DLP and data governance, the controlled boundary must include model inputs, retrieval results, prompts, generated outputs, recipients, external endpoints, inter-Agent messages, and skill registries. NIST and OWASP identify data privacy, human-AI configuration, identity and privilege abuse, tool misuse, memory or context poisoning, and insecure inter-Agent communication as connected governance concerns [8,9]. A sensitive read can be permitted while an external transformation or cross-department summary is denied because the purpose or recipient is outside the current authorization. Audit records should preserve both the policy decision and the data-flow edge.

For procurement and deployment, vendor Agents should first run in an offline or synthetic-identity sandbox with tool and resource allowlists. Tests should include benign tasks, indirect injection, delayed approvals, contaminated skills, cross-Agent messages, rollback, and kill-switch behavior. Production rollout should require tenant isolation, short-lived credentials, high-impact approval, rate limits, and evidence retention. The business trade-off is a risk-cost frontier containing token cost, p95 latency, task success, false refusal, review effort, and expected damage. Low-risk simulation can use the faster batch path, while high-risk actions require event-level evidence that can reconstruct authority, source, and state impact.

6 讨论

6.1 研究意义

Morpheus-Harness 将企业内部威胁模拟从账号级事件扩展为可审计的执行链。相关链路可以表示为 `来源 → 人类主体 → 委托的 Agent/运行时 → 工具/API → 资源或接收者 → 持久化记忆`。一次操作可能同时涉及外部文档或消息、员工、规划器、工具 Agent、委托令牌和改变状态的服务。OAuth 令牌交换和基于属性的访问控制已经提供了区分令牌主体与实际行动方、并根据主体、对象、操作、环境和策略判断授权的机制 [4,7]。Morpheus-Harness 将这些区分带入生成的企业轨迹，并把组织目的和依赖关系加入审计单元 [6]。

当前实现通过层级规划、human-planner 到 tool-agent 的交接、Agent 注册表字段、`harness_events.jsonl`、`agent_audit.jsonl`、`behavior_policy.csv`、按成员保存的技能文件和事件级轨迹记录，使这条链路可被观察。规模化运行器还展示了一个有界执行路径。在 stub 回归中，100 名员工运行 13 周会产生 26,000 个计划事件和 100 个员工批次，失败批次为零。这说明系统具有可复现的工程路径和产物边界。13,000 个潜在复杂事件入口减少到 100 个员工批次，表示模型入口粒度降低，并不意味着真实模型时间、token 使用量或货币成本降低了 130 倍。

方法论上的主要意义在于区分轨迹有效性与检测器效用。检测器在生成数据上表现良好，只能说明这些数据支持该检测器和任务，不能证明生成行为复现了真实员工。直接评测还必须分别衡量分布和条件行为、组织和时间一致性、来源完整性、干预局部性、可执行状态变化以及下游检测效用 [17,20]。当前系统仍然是受控模拟器。攻击由 `src/harness_runner.py` 从 `threat_scenarios/` 选择，部分轨迹保留 `Attack`、`attack_marked` 或 `(Attack)` 标记，路由器基于关键词，长周期批处理也不能复现所有实时的跨员工交互。因此，当前证据不足以支持真实世界攻击发生率的结论，也不足以支持企业 Agent 必然增加风险的判断。

6.2 未来工作

第一项工作是将日程级攻击注入转变为交互级内生威胁。基准应从同一组织状态生成四种匹配条件：普通员工行为、良性 human-agent 工作、Agent 介导的威胁和传统账号级威胁。单个 `do()` 干预只能改变来源、委托范围、记忆条目、Agent 间消息或意图中的一个变量。员工和 Agent 应自行决定是否询问、等待、委托、重试或继续执行，同时允许威胁失败。评测需要区分预配置活动、被拒绝请求、被阻止尝试、部分泄露和已验证的状态变化。指标应包括攻击成功率、受影响资源状态、检测延迟、错误拒绝、来源完整性、归因歧义、持久性和因果局部性。这一设计借鉴动态工具使用评测和间接提示注入研究 [10,11,23,24,28]。

第二项工作是统一 Harness。追加写入的事件总线和共享状态存储应携带组织状态版本、父事件、主体与运行时身份、委托链、来源对象、计划步骤、策略决策、工具结果、记忆写入和接收者。约束与来源验证器应在每次工具调用前检查授权，在执行后验证后置条件，并支持检查点、分支、确定性回放、回滚和状态差异分析 [27]。这是必要的，因为当前产物可能互相矛盾。一次运行中，工具日志报告证据不可用，而日摘要却称证据已经审核并归档。当前实现还可能在 Harness 返回失败答案后追加 `task_completed`。生命周期事件或自然语言摘要都不应被视为业务结果已经完成的证明。

第三项工作是将关键词路由器和轻量技能存储升级为面向安全的控制机制。经过校准的风险—复杂度门控应估计复杂度、风险、不确定性、预期成本和错误拒绝成本，再选择确定性执行、规划—执行、人工复核或 abstention。`legacy workflow memory` 应升级为受来源约束的技能自动机，加入激活条件和前置条件、带类型的工具边、后置条件、权限与接收者范围、来源轨迹、版本、有效期、验证、撤销和污染状态。实验应在固定任务和工具权限的条件下，比较员工隔离、部门共享、全组织共享和污染记忆。指标包括污染率、传播深度、恢复时间、未授权调用次数和撤销后的任务效用 [21,25,26]。

第四项工作是验证外部有效性。未来实验应在同一个世界状态上比较事件级执行和长周期批处理，在不同组织、模型、工具和留出时间段之间进行迁移，并使用 CERT、LANL 和 Enron 记录校准时间与通信图 [2,29,30]。还应评测成员推断、重构攻击、身份泄露、模型漂移、供应商故障、p50 与 p95 延迟、token 成本和重试恢复。发布的产物应继续默认使用合成身份、离线工具和明确的威胁预算。

6.3 对当前企业发展的影响

在 IAM 方面，企业 Agent 应被作为可识别、可委托的主体进行治理。生产记录应包括 Agent 身份、所有者或发起人、生命周期状态、运行时身份、token 范围、资源范围、人类主体、委托链、目的和有效期。实际控制应采用绑定目的的最小权限、短期委托和明确的接收者限制。Microsoft Entra Agent ID 与 OAuth 令牌交换展示了如何分别表示令牌主体和实际行动的 Agent [7,13]。零信任和基于属性的访问控制则为检查当前用户、Agent、资产、资源、操作和工作流上下文提供策略基础 [4,5]。

在 SOC 和 UEBA 方面，分析单元应从用户—账号对扩展为来源到状态的完整链路。调查员需要看到来源、检索对象、prompt 或消息、人类主体、Agent 与运行时、技能版本、工具调用、接收者、策略决策和最终状态。用户与资源上下文已经能够改善内部威胁检测 [15]，对 AI 操作账号的监测也表明，有状态影响和有限的每日复核预算会改变实际召回能力 [18]。因此，告警排序应综合影响程度、不确定性、来源完整性、归因歧义和复核成本。模型解释可以辅助分诊，但影响确认应依靠服务状态和策略证据。

在 DLP 和数据治理方面，受控边界必须覆盖模型输入、检索结果、prompt、生成输出、接收者、外部端点、Agent 间消息和技能注册表。NIST 与 OWASP 将数据隐私、人机配置、身份与权限滥用、工具误用、记忆或上下文污染以及不安全的 Agent 间通信视为相互关联的治理问题 [8,9]。读取敏感数据可以被允许，但由于目的或接收者超出当前授权，将其发送给外部模型或生成跨部门摘要可以被拒绝。审计记录应同时保存策略决策和数据流边。

在采购与部署方面，供应商 Agent 应首先在离线或合成身份沙箱中运行，并使用工具和资源白名单。测试应包含良性任务、间接注入、延迟审批、污染技能、跨 Agent 消息、回滚和 kill switch 行为。生产上线应要求租户隔离、短期凭据、高影响操作审批、速率限制和证据留存。企业需要优化的是风险—成本前沿，其中包括 token 成本、p95 延迟、任务成功率、错误拒绝、复核成本和预期损失。低风险模拟可以采用更快的批处理路径，而高风险动作需要事件级证据，以重建权限、来源和状态影响。
