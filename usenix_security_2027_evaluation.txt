5 EVALUATION

This section evaluates Morpheus-Harness as a generator of AI-mediated enterprise insider-threat data. The protocol separates dataset realism from downstream insider-threat detection. Dataset realism is evaluated directly from the generated traces and their audit relations. ITD utility is evaluated by running established detectors on the same employee-day sampling budget used for the comparison datasets.

The evaluation answers three questions.

RQ1. Does Morpheus-Harness preserve the temporal, complexity, diversity, and organizational behavior properties measured by prior enterprise behavior simulation work?

RQ2. Does Morpheus-Harness preserve the existing temporal, complexity, diversity, and organizational indicators when compared with the fixed reference datasets?

RQ3. Do the open-source MOLE-Cascade and MOLE-RLM monitors detect threats on CERT and the three Morpheus-Harness scenarios, and does Agent-aware evidence improve classical ITD metrics on the same Morpheus-Harness test employees?

The protocol follows a serial spine with parallel branches inside each stage. The first stage completes all source preparation and generation. The second stage completes and freezes the four realism indicators for all sources. The third stage evaluates CERT and the three Morpheus-Harness scenarios with ITD methods. A later stage cannot start until every branch in the current stage has completed.

5.1 Dataset preparation

5.1.1 Morpheus-Harness data

Each Morpheus-Harness dataset unit contains 100 employees and 50 working days. The workday is fixed to 10:00--19:00. Each employee has one Personal Agent. The organization has one shared Enterprise Agent with an explicit role, tool allowlist, authority scope, memory scope, and resource scope. The basic sample unit is an employee-day.

    100 employees x 50 working days = 5,000 employee-days per unit.

Each unit targets 4,000 benign employee-days and 1,000 insider-threat employee-days. The threat subset is approximately balanced over the three threat families, with 333, 333, and 334 samples. Threat labels, intervention identifiers, authorization verdicts, and provenance evidence are stored outside detector inputs.

We use one generator model across the three scenarios.

- Generator: deepseek-v4.1-flash with max reasoning.
- S1: internet company.
- S2: financial institution.
- S3: AI company.

The three independent scenario units contain 15,000 target employee-days in total. Every unit has an independent employee-profile directory, organization configuration, Agent registry, schedule tree, Skill/Memory store, random seed, and output directory. No unit reads another unit's generated state.

Benign employee-days can contain login, email, web, file, calendar, task, Personal Agent, Enterprise Agent, human-to-Agent handoff, Skill, Memory, and audit events. Threat employee-days retain the employee role, schedule context, and ordinary work pressure of their matched benign conditions. The generator applies the threat intervention to a recipient, delegation scope, approval state, source object, data combination, or Skill/Memory context and records the resulting state change.

5.1.2 Dataset sources and fixed evaluation slices

We use fixed 5,000-record slices for CERT, TWOS, UNM, and ChimeraLog. Morpheus-Harness contains 15,000 records, with 5,000 records for each of the three organization scenarios. The native unit and label semantics are retained in the manifest because the sources were not created with the same Agent-aware schema.

ChimeraLog is generated with deepseek-v4.1-flash in the internet-company scenario and then fixed to a 5,000-record evaluation slice. Morpheus-Harness is generated with the same model across the internet, financial, and AI scenarios.

| Dataset | Target size | Native sample unit | Native threat labels | Role |
|---|---:|---|---|---|
| Morpheus-Harness | 15,000 total, 5,000 per scenario | employee-day | 12,000 benign / 3,000 threat | Primary AI-mediated enterprise dataset |
| ChimeraLog | 5,000 generated records | employee-day or closest published user-day unit | Use generated labels and fixed evaluation slice | Realism-only predecessor |
| CERT Insider Threat Test Dataset | 5,000 | user-day after canonical aggregation | Use official malicious/background labels | Sole external ITD baseline |
| TWOS | 5,000 | participant/session-day or closest published unit | Use native labels | Realism-only reference |
| UNM User Command/Masquerade Dataset | 5,000 | user command/session unit | Use native labels where available | Realism-only reference |

TWOS and UNM participate in the realism comparison. CERT is the sole external ITD baseline. Their different modalities are handled by dataset-specific canonicalization adapters. The detector never receives the dataset identifier as a feature.

The release manifest records source version, snapshot identifier, sampling seed, canonicalization script, selected record count, native label count, missing modalities, and the mapping from native fields to the common schema. A 5,000-record slice means a fixed evaluation budget. It does not imply that the sources have identical native schemas or identical numbers of raw events.

5.1.3 Canonical views and leakage control

The Common view contains fields that can be aligned across the sources, including principal, timestamp, event type, application or command family, resource when available, session, source, target, and outcome. Missing native fields are marked unavailable and are never filled by a generated value.

The Agent-aware view adds human principal, Employee Agent, Personal Agent, Enterprise Agent, owner, delegation chain, authorization decision, authority scope, memory scope, Skill identifier and version, source provenance, tool, recipient, and state outcome. The Agent-aware view is evaluated on Morpheus-Harness. The legacy datasets participate in Common-view evaluation unless they genuinely expose a comparable field.

The following fields are held out from detector input: dataset identifier, model identifier, scenario identifier, threat family, attack identifier, intervention identifier, direct benign/threat label, and post-hoc evaluation verdict. Employee or user partitioning is performed before feature extraction. A subject appears in only one of train, validation, and test.

5.1.4 Splits and repetitions

For every labeled dataset, subjects are split into 60% training, 20% validation, and 20% test subjects. Thresholds and early stopping are chosen on validation subjects only. The same subject split is used for Common and Agent-aware views on Morpheus-Harness.

Every ITD result is repeated with five fixed seeds. We report mean, standard deviation, and 95% bootstrap confidence intervals. Paired bootstrap is used when Common and Agent-aware views are evaluated on the same test employees.

5.2 Evaluation route I: dataset realism

5.2.1 Integrity checks

Before calculating realism metrics, we report the following data-quality checks.

- File and JSONL parse success.
- Required-field completeness.
- Event, employee-day, Agent, Skill, and Memory identifier uniqueness.
- Timestamp validity and chronological order.
- Schedule-to-execution consistency.
- Employee-to-Agent and Agent-to-resource reference completeness.
- Threat-label and threat-family consistency.
- Human-principal and executor recoverability.

Integrity checks describe whether the data can be used. They are reported separately from realism scores. Failed records are counted and documented rather than silently removed.

5.2.2 Four realism indicators

We use the four quantitative realism indicators from the Chimera evaluation. No additional primary realism metric is introduced.

24-hour temporal distribution. For each user or employee-day, event counts are placed into 24 hourly bins and normalized into a histogram. We report the distribution of activity across working hours, lunch hours, evening hours, and overnight hours. The same binning and event inclusion rules are used for CERT, TWOS, UNM, ChimeraLog, and Morpheus.

Within-modality user behavior diversity. For each user u and comparable log modality, let p_u(a) be the empirical probability of action a in vocabulary A. Behavioral entropy is

    H_u = - sum_{a in A} p_u(a) log p_u(a).

We report per-user entropy distributions and macro-average entropy separately for logon, email, web history, and file operation logs. A comparison is made only when the modality exists in both sources.

Cross-modality event correlation. For a common user-day or time window, we calculate event co-occurrence or correlation between pairs of available modalities, including logon, email, web history, and file operation activity. We report the modality-pair matrix and its average over available pairs. This measures whether events across log types form a coordinated activity pattern.

Behavior complexity. For each serialized user sequence S_u, we use the normalized compression ratio

    C_u = 1 - L_compressed(S_u) / L_raw(S_u),

where L_compressed is the gzip-compressed length and L_raw is the original sequence length. Higher C_u indicates lower redundancy and greater sequence complexity.

5.2.3 Reference-first comparison and scenario analysis

After all source preparation and generation tasks complete, the four realism indicators are run in parallel across CERT, TWOS, UNM, ChimeraLog, and the three Morpheus scenarios. The frozen results define the comparison ranges for the full realism analysis.

After ChimeraLog and Morpheus generation, the same four indicators and the same canonicalization rules are applied to their evaluation slices. Fields that do not exist in a reference dataset remain unavailable. Agent-specific fields are reported as Morpheus-specific descriptive fields and are not converted into synthetic values for the reference datasets.

The single generator model is evaluated separately in the internet-company, financial-institution, and AI-company scenarios. The organization configuration, employee count, workdays, threat ratio, random seed family, canonicalization, and reference split are fixed. We report the four indicators separately and do not construct a new combined realism score.

5.3 Evaluation route II: insider-threat detection

5.3.1 Detection methods

We evaluate two open-source monitors from the MOLE repository using a frozen repository commit, preprocessing adapter, and configuration. MOLE is a recent benchmark for detecting insider activity by AI-operated accounts. Its repository provides the monitor interface, replay code, audit-event schema, label alignment, and evaluation scripts under an Apache-2.0 license.

MOLE-Cascade is the cost-bounded two-stage monitor. It ranks all account-days with a low-cost screen and escalates only the selected fraction to the semantic LLM judge. MOLE-RLM is the recursive Agent monitor. It investigates an account-day with iterative evidence access and historical context before returning a suspicion score and rationale. Both monitors consume the same canonical account-day event interface.

CERT user-days are adapted to MOLE account-day events. Morpheus employee-days are adapted from the employee, Agent, tool, authorization, provenance, and outcome logs. The common input view exposes only fields available in the corresponding source. Neither detector receives dataset identifier, model identifier, scenario identifier, threat-family label, attack identifier, direct benign/threat label, or post-hoc adjudication.

5.3.2 ITD tasks and baseline use

D1, in-domain detection. Fit and test MOLE-Cascade and MOLE-RLM separately on CERT, Morpheus internet, Morpheus financial, and Morpheus AI. Report the six classical metrics for each dataset.

D2, scenario comparison. Compare the three Morpheus scenarios with the CERT baseline under the same Common view, subject partition, threshold protocol, and five seeds.

D3, Agent-aware increment. On identical Morpheus-Harness employee-day test subjects, compare Common view with progressively added Agent identity, delegation and authorization, and Skill/Memory provenance for both MOLE monitors. The increment is reported using the same classical metrics.

TWOS, UNM, and ChimeraLog are used for realism only. ITD results cover CERT and the three Morpheus scenarios. We report results per dataset because the native modalities and label semantics are different.

5.3.3 Classical ITD metrics

Let TP, FP, TN, and FN be the standard binary classification counts.

    Accuracy = (TP + TN) / (TP + TN + FP + FN)
    Precision = TP / (TP + FP)
    Recall = TP / (TP + FN)
    F1 = 2 * Precision * Recall / (Precision + Recall)
    FPR = FP / (FP + TN).

ROC-AUC and PR-AUC are calculated from the continuous detector scores. PR-AUC is emphasized because the threat class is smaller than the benign class. No new operational metric is introduced. The Agent-aware increment is reported as the difference in F1 and PR-AUC between the paired views.

5.4 Statistical reporting and artifacts

Every result manifest records dataset version, model, scenario, source slice, subject split hash, detector version, feature view, seed, threshold procedure, valid sample count, excluded record count, and failure count. API keys, passwords, and raw sensitive parameters are excluded.

Required artifacts include raw_events.jsonl, employee_day.csv, trajectory.jsonl, logon.csv, email.csv, web_history.csv, file_operation.csv, harness_events.jsonl, agent_audit.jsonl, skill_provenance.json, final_schedule.csv, agent_registry.json, hierarchy.json, threat_labels.jsonl, manifest.json, data_quality_metrics.json, and downstream_results.json.
